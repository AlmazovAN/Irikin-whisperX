# P22 / GitHub PR #23 — человекочитаемый TXT стенограммы

**База:** `master` после P21 / GitHub PR #22:
`f33bd27c68d6ec85c058e709679071c36bb8d7fc`.
**Ветка:** `feature/p22-transcript-txt-format`.

## Установленное расхождение

В P12 (GitHub PR #13) уже реализован отдельный TXT writer
`modules/jobs/results.py:render_txt()`, а в P17
`modules/jobs/artifacts.py:publish_result_set()` уже записывает
`transcript.json` и `transcript.txt` из **одного нормализованного payload**.
Не требуется новый exporter, новый ASR, изменение BaseTranscriptionPipeline,
модификация Gradio или фонового worker.

Однако до P22 TXT содержал интервал
`[HH:MM:SS.mmm --> HH:MM:SS.mmm] SPEAKER_00: текст`, что не соответствовало
утверждённому краткому формату MVP.

## Контракт для новых TXT

```text
[00:00:12] [SPEAKER_00]: Добрый день
[00:00:14] [SPEAKER_01]: Здравствуйте
[01:00:01] Реплика без установленного спикера
```

- В каждой строке указан **start** сегмента в формате `HH:MM:SS`.
  Дробная часть **отбрасывается вниз** (`12.999 → 00:00:12`), поэтому
  метка не становится позже фактического начала. Записи дольше 24 часов
  допустимы: часы увеличиваются.
- Когда поле `speaker` присутствует, оно явно выделено квадратными
  скобками (`[SPEAKER_00]:`). Если поле `speaker=null`, **не выдумываем**
  идентификатор говорящего, оставляем реплику без метки.
- Переносы строк и повторные пробелы внутри одной реплики превращаются
  в один пробел; одна реплика соответствует одной строке TXT.
- Дублирующий legacy-префикс `SPEAKER_00|` убирается
  существующим `normalize_segments()`, не вторым регулярным выражением.
- Пустые сегменты исключаются на этапе нормализации; отсутствие
  обязательного `start` даёт `INVALID_TIMESTAMP`, а не фиктивное время
  и не `COMPLETED`.
- `transcript.json` остаётся `schema_version=1`, в нём сохраняются
  **точные** `start` и `end` с дробными секундами, поля `speaker`,
  `text`, `words` и confidence при наличии.
- `modules/utils/subtitle_manager.py:WriteTXT` (plain text для
  старого WebUI) **не изменяется**. Не смешивать эти назначения.

## Совместимость и сохранность

Новый формат применяется только к **новым** вызовам `render_txt`,
`write_result_files` и `publish_result_set`. Ранее опубликованные
`result/attempt-N/` с другим видом TXT сохраняются без изменений,
их SHA-256 manifest и прежний `JobService.get_artifact()` продолжают
проверяться. Переэкспорт существующего JSON как отдельное действие
относится к следующей функциональности и пока не добавлен.

Готовность результата определяется старым P17 протоколом:
оба файла + manifest публикуются атомарным переименованием, хеши
проверяются, затем worker выставляет `COMPLETED`.
UI-кнопка скачивания появляется только в P23 (следующем PR плана).
Смены миграций SQLite, REST и lifecycle модели нет.

## Проверки

- `tests/unit/test_normalized_results.py`: обновлены старые ожидания TXT.
- `tests/unit/test_mvp_transcript_txt.py`: точный формат, временные
  границы, две метки спикеров, `speaker=None`, ошибка отсутствующего
  `start`, разовый экспорт и durable publishing из одного payload.
- Интеграционный автономный тест: реальная очередь SQLite + файловая
  система + `JobWorker` с имитацией модели; после `COMPLETED` TXT/JSON
  читаются через `JobService.get_artifact()` и согласуются по тексту.
- Наследованный `WriteTXT.write_result` проверяется на неизменность
  отдельного plain-text режима без тяжёлого импорта `gradio`.
- GitHub Actions Python 3.10/3.11/3.12 проверить перед merge.
  Реальный Windows + WhisperX + Pyannote + двухголосное аудио
  **не испытаны**; это требование P25.
