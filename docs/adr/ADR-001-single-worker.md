# ADR-001 — единый владелец inference-runtime

- **Дата:** 2026-10-16
- **Статус решения:** Accepted (архитектурное решение; реализация в P07–P25)
- **Область:** локальное Windows-приложение WhisperX с браузерной оболочкой
- **Связанный PR:** P06, этап 0

## Контекст

Унаследованный форк содержит два пути исполнения: Gradio `app.py`
создаёт `WhisperXInference` через `WhisperFactory`, а отдельный FastAPI
`backend/main.py` и `backend/routers/transcription/router.py` создают
свой `FasterWhisperInference` и используют `BackgroundTasks`. Эти два
пути **не объединены** общей очередью или владением памятью GPU/CPU.
Запуск их одновременно потенциально создаёт два тяжёлых экземпляра модели.

План MVP требует работы при закрытой вкладке, одной очереди,
сохранения входа и результата на диск, статуса после перезапуска,
Whisper Small `ru/transcribe` и диаризации. Предполагаемое оборудование
владельца — Windows 11, Ryzen 5 5500U, встроенная AMD Radeon, 8 ГБ RAM.
Это **заявленные характеристики**, не результат аппаратного тестирования.
На таком ПК нельзя предполагать наличие NVIDIA CUDA или запас памяти
под параллельную загрузку моделей.

## Решение

**Выбираем один локальный сервер Python и один общий job-runtime,
владеющий моделью и исполнением, с ограничением concurrency = 1.**

1. **Сервер/вход:** `Start.bat` из P05 запускает один `app.py`
   по `127.0.0.1`. Он не запускает отдельно Uvicorn/FastAPI.
2. **Интерфейс:** Gradio показывает загрузку, статус и скачивание.
   После MVP-рефакторинга обработчик UI только сохраняет файл и
   ставит задание в сервис; он **не вызывает** inference напрямую.
3. **Сервис заданий:** `JobService` (проектируемый в P13–P19)
   предоставляет `submit(id, file, preset)`, `get_status(id)`,
   `list_jobs()`, `get_artifact(id)`, `retry(id)`.
   Это контракт, **не уже существующий класс** в P06.
4. **Очередь/worker:** внутри того же локального серверного процесса
   один выделенный worker последовательно выполняет ровно одно
   тяжёлое задание. Только worker создаёт и использует экземпляр
   модели. Gradio и будущие REST-ручки обращаются к общему сервису,
   но не получают прямой доступ к объекту `WhisperXInference`.
5. **Pipeline:** переиспользуется
   `modules/whisper/base_transcription_pipeline.py` и
   `WhisperXInference/WhisperXWrapper`. **Не пишем параллельный**
   WhisperX-конвейер и не подключаем второй GPU-owner. Smoke P06
   вызывает этот путь напрямую как диагностику до реализации сервиса.
6. **Persistence:** исходник сохраняется атомарно в
   `data/jobs/<uuid>/input/` **до** enqueue; состояние — SQLite;
   `transcript.json` и `transcript.txt` записываются сначала
   во временные файлы, затем атомарно заменяются на финальные.
   Данные заданий **не** хранятся в автоочищаемом `backend/cache`.
7. **Восстановление:** `QUEUED`, `IN_PROGRESS`, `COMPLETED`,
   `FAILED`, `RETRYING` имеют явные переходы. После аварийного
   старта `IN_PROGRESS` не выдаётся как успешное: сохраняется
   диагностическая причина и выбирается управляемый retry.
   Никакой автоматической параллельной обработки при рестарте.
8. **Закрытие вкладки:** после подтверждения сохранения исходника и
   enqueue выполнение не зависит от состояния вкладки браузера.
   **Закрытие окна сервера, выключение/сон ПК прерывают работу**;
   возобновление — через persisted job/state, не магическое
   продолжение незавершённого GPU-вычисления.
9. **Модели:** начальный профиль только `small`, `ru`,
   `transcribe`, CPU/int8 по умолчанию. CUDA только после
   фактической NVIDIA-проверки. WhisperX alignment и Pyannote
   diarization выполняются тем же владельцем. До полноценного
   smoke-теста нельзя объявлять их совместимыми на 8 ГБ.
10. **Secrets:** `HF_TOKEN` и последующие OAuth-токены берутся из
    приватного локального хранилища/окружения. Не писать значения в
    `Task`, журналы, `README` или PR. Текущую tracked
    `backend/records.db` не использовать как новую БД задач
    до миграции/аудита.

## API/service границы

```text
[Browser 127.0.0.1] ←→ [Gradio UI / optional REST adapter]
                                 │
                                 ▼
                   [JobService + durable SQLite]
                                 │ enqueue
                                 ▼
                   [single in-process worker]
                                 │
             [VAD → WhisperX ASR → alignment → Pyannote]
                                 │
                   [atomic TXT/JSON artifacts]
                                 │
                     [JobService status API]
```

Обязательное правило: ни один adapter UI/API не создаёт параллельный
ASR/diarization model. Число одновременно выполняемых тяжёлых задач
равно **1**, пока нагрузочные испытания не позволят пересмотреть его.
Очередь задач и их приём не равны параллельности inference.

## Рассмотренные альтернативы

| Вариант | Решение | Почему |
| --- | --- | --- |
| Gradio и FastAPI независимыми процессами с собственными моделями | Отклонено для MVP | Дублирование памяти и несогласованный жизненный цикл заданий |
| Celery + Redis + отдельный GPU worker | Отложено | Лишняя инфраструктура для одиночного Windows-ПК и первого MVP |
| ASR внутри браузера | Отклонено | Не соответствует существующим Python/WhisperX/Pyannote-модулям |
| Один Gradio-процесс, но прямой вызов ASR из UI callback | Только legacy-диагностика | Закрытие/рестарт браузера и статусы требуют общего persisted job service |
| Один Python-сервер + единый worker + durable queue | **Принято** | Управляемая память, надёжные статусы, минимальная локальная инфраструктура |

## Последствия и реализация

**Положительные:** один владелец моделей; проще отслеживать память и
ошибки; после загрузки задания можно закрывать вкладку; проще
восстановление и аудит результата. **Компромиссы:** обработка
последовательная; аварийное завершение worker прерывает текущую
инференцию; при подвисшем GPU/CPU процессе может потребоваться
дополнительная изоляция в будущем.

Текущий P05 лишь поднимает один Gradio-сервер; наличие одного сервера
**ещё не означает**, что реализованы durable queue и отдельный worker.
P06 утверждает архитектуру, а **не вводит** эти компоненты в работу.

### Реализационные этапы

- **P07–P12:** MVP preset Small/ru, входной файл, единый выход,
  жёсткая проверка ASR/alignment/diarization и TXT/JSON writer.
- **P13–P19:** durable SQLite и job API, atomic storage, ровно один
  inference-owner/worker, восстановление и тесты close-tab.
- **P20–P25:** новая простая Gradio-оболочка, единый статус,
  история, скачивание, сквозные тесты и MVP gate.
- FastAPI legacy endpoints не удалять до регрессионной проверки;
  позже переадресовать на JobService или деактивировать
  конкурентный inference-путь.
- Старая многостраничная Gradio оболочка остаётся доступна
  для диагностики до полноценной замены; прямые legacy callback
  нельзя параллельно запускать с MVP-worker.

## Критерии пересмотра

Рассматривать иной worker/process-модель только при фактических
измерениях RAM/VRAM и после сквозных тестов. Нельзя одновременно
держать два владельца GPU «на всякий случай» или повышать
concurrency по желанию без доказанной безопасности и наблюдаемости.
