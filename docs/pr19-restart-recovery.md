# PR19 / P18 — восстановление очереди после аварийного завершения

Дата: 2026-10-17. Основание: master после PR18,
SHA `356791b4e4f5e1cdc5e7e2158b34980d708eca3b`.

## Сценарий

Приложение хранит входное аудио и задания в data/jobs/, а результат каждой
попытки — атомарным набором JSON + TXT + manifest (PR18). При аварии
между началом ASR и записью COMPLETED в SQLite остаётся IN_PROGRESS.
Это **не** означает, что необходимо заново запускать модель: на диске
уже может быть пригодный результат.

## Алгоритм восстановления

1. JobWorker.start() получает межпроцессную блокировку .worker.lock.
   Пока другой worker работает, блокировка не выдаётся; активное
   IN_PROGRESS **не считается аварией**.
2. В единой транзакции BEGIN IMMEDIATE читаются Task в порядке ID.
   Записи QUEUED, FAILED, CANCELLED, COMPLETED не переписываются.
3. Для каждого IN_PROGRESS текущего attempt:
   - Если в result/attempt-N лежит **полная проверенная тройка**
     transcript.json + transcript.txt + manifest.json с корректными
     контрольными суммами, статус переводится в COMPLETED / DONE,
     progress=1.0, сохраняются относительные пути обоих файлов.
     Запуск WhisperX **не повторяется**.
   - Если готового результата нет, статус становится INTERRUPTED,
     error_code=RECOVERY_INTERRUPTED, остаётся достигнутая точка прогресса.
   - Если каталог результата существует, но не проходит проверку SHA-256,
     версия/структура неверна или обнаружена symlink-подмена:
     INTERRUPTED / RECOVERY_OUTPUT_UNVERIFIED. Повреждённые файлы
     остаются для диагностики и не выдаются через get_artifact.
4. Транзакция SQLite завершается до запуска фонового потока. При ошибке
   обновлений происходит rollback всего набора, worker не запускается,
   блокировка освобождается. Нет частично восстановленной очереди.
5. После восстановления worker продолжает выполнять уже существующие
   QUEUED строго FIFO. INTERRUPTED не исполняются автоматически.

## Повторная постановка

JobService.retry(uuid) теперь принимает FAILED и INTERRUPTED **только**
при доступном ранее сохранённом исходнике. Новая попытка:
- явное пользовательское действие, не автоматическое;
- сбрасывает stage=QUEUED, progress=0, error/error_code, started_at,
  finished_at и пути результата;
- сохраняет исторический attempt до нового claim, при котором attempt
  увеличится на единицу;
- сохраняет результаты прежних попыток на диске (никогда не перезаписывает
  готовый каталог).
Если исходник исчез, retry возвращает False; запись INTERRUPTED сохраняется.

## Незавершённые файловые операции

Read-only осмотр data/jobs:
- каталоги с UUID, не упомянутыми в tasks, считаются orphan job folders;
- временные .attempt-N-pending-<random> в result/ считаются незавершёнными
  наборами, независимо от статуса задания;
- количество фиксируется в неизменяемом RecoveryReport с полями
  completed_from_artifacts, interrupted, unverified_outputs,
  queued_preserved, orphan_job_directories, unfinished_output_directories.

Ни один orphan, неполная стенограмма, исходный аудиофайл, история
повторов или запись SQLite **не удаляется автоматически**. Отчёт не
содержит путей, имён файлов, аудиотекста и токенов.

## Границы и риски

- Сканирование и восстановление запускаются только из JobWorker.start()
  после успешного lock; не подключаются к app.py параллельно с legacy
  Gradio-ASR. Ручной вызов внутренней функции вне lock недопустим.
- Никакого продолжения инференции с предыдущего фрагмента / GPU state.
  Нужен полный повтор новой попыткой.
- Не исправляем повреждённые COMPLETED старых версий и не мигрируем
  архив без manifest: доступ к ним остаётся на проверке get_artifact().
- При внезапном отключении питания на Windows записи на диске могут
  не пережить сбой физически; проверка манифеста не является резервным
  копированием.
- Возврат интерфейса к persisted queue, кнопка retry и диалоги
  удаления планируются далее; auto retry намеренно исключён.

## Тесты

tests/unit/test_restart_recovery.py выполняет реальные SQLite, потоки,
файловые операции и lock (модель, ffprobe имитируются). Покрываются
сбой до и после публикации, успешная проверка hash, порча manifest,
конфликт второго worker, idempotency, orphan/temp, ручной retry,
повреждённый исходник и rollback SQLite при ошибке.
Проверки Windows/NTFS + Pyannote остаются NOT_RUN.
