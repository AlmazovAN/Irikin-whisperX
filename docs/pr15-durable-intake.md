# PR15 / P14 — надёжный приём локального аудио

- Дата: 2026-10-16
- План: P14; фактический номер GitHub PR: #15
- База: PR14 squash в master (1b862556a5bd29cccfdd07297b4eef889d3da07e)
- Граница: сохранение исходника и атомарный приём QUEUED. **Нет worker или browser UI**.

## Контракт

Для нового локального job-runtime используется отдельная, игнорируемая Git
база data/jobs/jobs.sqlite3. Исторический backend/records.db не трогается.
Подключение новой базы выполняется через стандартную библиотеку sqlite3 и
версионированную миграцию, созданную в PR14.

Вызов JobService.submit(InputSource.upload(...)) или
JobService.submit(InputSource.local_file(...)) выполняет следующую цепочку:

1. Авторизует входной путь согласно доверенным upload_roots/local_roots,
   проверяет формат, размер и длительность через существующий P08 FFprobe.
2. Генерирует UUID, создаёт индивидуальный каталог data/jobs/<uuid>/input/.
3. Повторно проверяет открытый источник и его метаданные; потоково копирует
   файл в закрытый .part с ограничением размера, делает fsync и атомарный rename.
4. Повторно валидирует **сохранённую копию**, чтобы после исчезновения
   Gradio-cache исходник оставался пригоден для обработки.
5. Только после сохранения выполняет транзакцию SQLite с присвоением
   QUEUED, stage=QUEUED, Small/ru/transcribe. Возвращает безопасный
   JobTicket (UUID, статус, имя, модель, язык, длительность и дата).

После удаления временного Gradio-файла, закрытия вкладки или создания нового
экземпляра JobService исходная запись доступна по UUID; JobService.saved_input
предоставляет проверенный путь только внутреннему коду будущего worker.

Одинаковые оригинальные имена не вызывают перезапись: каждый job имеет отдельный
UUID и дополнительное уникальное имя файла. В БД сохраняется приватный
относительный путь, не выводимый в публичном JobTicket.

## Сбои и гарантия

- Ошибка проверки, чтения или записи не приводит к появлению QUEUED.
- Неудачная SQLite-транзакция удаляет каталог только своего ещё не принятого job.
- Уже принятые задания и чужие файлы не очищаются этой процедурой.
- На границе файловой системы и SQLite нет общей атомарной транзакции:
  аварийное завершение процесса между rename и INSERT может оставить
  **orphan-folder**, но не подтверждённое QUEUED-задание. Очистка и
  восстановление таких случаев — P18.
- Успешный submit означает сохранение входа **до** ответа клиенту.
  Закрытие браузера после ответа не удаляет его, но работа модели не
  запускается этим PR. Загрузка файла до submit всё ещё зависит от вкладки.

## Ограничения интеграции

Стартовый Start.bat использует Gradio app.py. В этом PR **не подключаем**
новый API к отдельно запущенному FastAPI backend/main.py, поскольку там остаётся
legacy FasterWhisperInference и BackgroundTasks (ADR-001 запрещает двух владельцев).
PR16/P15 плана подключит единственный worker и общий сервис; последующий UI
начнёт отправлять задания в этот сервис, а не в Gradio callback с inference.

Автономные тесты: python -m pytest -q tests/unit/test_durable_job_intake.py.
Проверяют независимость от временного файла, повторные имена, путь и symlink,
сбой копирования/БД, отсутствие QUEUED после ошибок и сохранность принятой задачи.
В CI FFprobe замокан, но копирование реальных bytes и SQLite не замоканы.
Windows, CPU WhisperX, Pyannote, браузерный upload и отключение питания —
NOT_RUN, требуют отдельного ручного испытания.
