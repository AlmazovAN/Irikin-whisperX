## Контракт сохранения

Отдельный модуль `modules/jobs/artifacts.py` публикует один неизменяемый
набор результатов для **каждой попытки**:

```text
data/jobs/<uuid>/
  input/<uploaded-audio>
  result/
    attempt-1/
      transcript.json
      transcript.txt
      manifest.json
    attempt-2/                      # Только после явного retry
      ...
```

Алгоритм `publish_result_set`:

1. Нормализовать исходный `TranscriptionResult` через существующий
   `build_result_payload` (PR13) и создать JSON/TXT из единого payload.
2. Записать оба файла во временный `result/.attempt-N-pending-<random>/`,
   проверить запись и `fsync` каждого файла.
3. Записать `manifest.json` с версией, попыткой, длиной и SHA-256
   каждого файла; `fsync` файла и временного каталога на POSIX.
4. Атомарно **переименовать каталог целиком** в `result/attempt-N/`
   на том же файловом разделе. На POSIX синхронизировать каталог-родитель.
5. Прочитать и проверить оба файла и manifest. Только затем в одной SQLite
   транзакции записать относительные пути и `COMPLETED` / 100%.

При известной ошибке до публикации удаляется только временный каталог,
выполненные ранее попытки и исходник **не трогаются**. Публикация никогда
не перезаписывает каталог уже существующей попытки. В случае сбоя SQLite
после публикации проверенный набор остаётся на диске, но статус не должен
ложно стать COMPLETED. Возможное `IN_PROGRESS` после аварии будет
разбираться в P18 плана (GitHub PR19).

**Гарантии:** атомарная видимость всей пары файлов при directory rename;
проверка от случайного повреждения файлов при чтении. Нельзя обещать полную
стойкость к выключению питания на Windows: стандартная библиотека Python
не даёт универсальной синхронизации каталогов на NTFS. SQLite тоже
отдельная транзакция, нет распределённой атомарности между SQLite и FS.

## Доступ к результатам

`JobService.get_artifact(uuid, format="json"|"txt")` — внутренний
метод серверной части. Он требует status=COMPLETED, сверяет сохранённые
в БД относительные пути с ожидаемыми, перепроверяет checksum и отдаёт
локальный Path. Приватные пути не раскрываются в `JobTicket`.

Если пользователь/программа изменили или удалили один из файлов, метод
завершится кодом `RESULT_CORRUPT`, а не выдаст повреждённую стенограмму.
Это **не HTTP-endpoint**; кнопка скачивания появится в Simple UI позднее.

## Retention (хранение)

**По умолчанию: бессрочно до явного действия пользователя.**
Никакого автоудаления через сутки, по сроку, из-за смены статуса,
ошибки обработки либо после закрытия вкладки. Сохраняются исходник,
результаты всех попыток и SQLite-запись в `data/jobs/`, который игнорируется
Git. Файлы не переносятся в Gradio cache или backend/cache.

Поскольку записи могут содержать конфиденциальные сведения, на локальном
ПК следует ограничить доступ к каталогу и контролировать свободное место.
Чистка по сроку/удаление через UI, подтверждение и безопасная очистка
нуждаются в отдельном контракте (P19/последующий UI PR). Никакой
автоматической деструктивной функции этим PR не вводится.

Незавершённые `.attempt-*-pending-*/` после жёсткого прекращения
процесса остаются как возможные orphan-артефакты для P18 recovery.
Повторную попытку сохраняем в `attempt-N`, не подменяя историю.

## Проверки и ограничения

Автономные тесты `tests/unit/test_atomic_job_artifacts.py`:
падение при записи второго файла, ошибка rename, контрольные суммы,
несовпадение manifest, отсутствие перезаписи, повреждение после
COMPLETED, удаление файла, подмена результата symlink, повтор,
сохранение после перезапуска и отсутствие автоматического удаления.
Проверки выполняются с настоящими SQLite/файловой системой,
без загрузки WhisperX. Реальная Windows/NTFS/Pyannote приёмка — NOT_RUN.
