# PR16 / P15 — единый FIFO-worker для WhisperX

- Дата: 2026-10-16
- Задача плана: P15, GitHub PR #16
- База: PR15 в master, cb7f3eef29a3b64f19245c7d4015223ddecd807d

## Реализованный контракт

JobWorker принимает **существующий** JobService с SQLite из PR15.
JobService.submit() сначала сохраняет файл и создаёт QUEUED; worker,
запущенный в отдельном потоке того же локального сервера, считывает
следующее задание из SQLite через BEGIN IMMEDIATE/ORDER BY id (FIFO).
Он вызывает один TranscriptionService, уже использующий существующий
VAD → WhisperX → alignment → Pyannote, а не новый ASR.

В реализации:

- Только один поток выполняет inference. Межпроцессная блокировка
  data/jobs/.worker.lock (msvcrt.locking на Windows, flock на Unix)
  предотвращает запуск второго владельца той же очереди. Файл блокировки
  не удаляется при release, поскольку владение — открытый descriptor.
- Claim изменяет QUEUED → IN_PROGRESS, увеличивает attempt; ошибки
  классифицируются по стабильным кодам и помечают FAILED.
- Если транскрипция успешна, writer PR13 создаёт JSON/TXT в
  data/jobs/<uuid>/result/, после чего worker ставит COMPLETED.
  **Важно:** P17 ещё должен заменить writer на полностью атомарный
  temp + fsync + rename механизм и утвердить retention.
- Порядок сохранён при одинаковых названиях и параллельных submit.
- Один сбой ASR или инициализации модели не блокирует следующий job.
- Worker.stop() перестаёт брать новые задания, но не прерывает текущую
  тяжёлую инференцию. stop(wait=False) не освобождает блокировку до её
  фактического завершения.
- Сервис предлагает list_jobs(), cancel() только для QUEUED,
  retry() только для FAILED при наличии оригинального файла.
  Тонкие сценарии отмены IN_PROGRESS/OOM/cleanup — P19.

## Защита от рестарта

При старте и при каждом claim наличие IN_PROGRESS означает, что требуется
recovery — worker не запускает ещё одну модель и не переводит зависшее
задание в COMPLETED. P18 реализует переход INTERRUPTED/RETRYABLE.
После аварийного завершения исходник, записи SQLite и успевшие сохраниться
артефакты остаются на диске, но продолжения с «секунды N» нет.

## Граница безопасности app.py

**Новый worker не включается автоматически в legacy app.py.**
Существующий Gradio App создаёт self.whisper_inf и непосредственно запускает
инференцию; одновременный запуск worker сделал бы два владельца CPU/GPU.
До переключения обработчиков UI на JobService нельзя параллельно
использовать legacy direct-ASR и JobWorker. В интеграционном PR
предусмотреть явный режим, исключающий этот конфликт.

Отдельный backend/main.py с FasterWhisperInference не запускаем.
REST task endpoints и автообновление статусов UI разрабатываются далее
(P16 по плану — PR17; P20–P21 по плану — Simple mode).

## Тесты

Автономный тестовый комплект tests/unit/test_single_job_worker.py:
реальная SQLite/файлы/потоки, искусственная ASR и FFprobe. Проверяется
FIFO, один владелец, сохранение обоих артефактов, отказ/повтор, отмена
QUEUED, запрет старта при зависшей IN_PROGRESS, остановка без потери
текущего задания, отказ модели и отсутствие утечки текста ошибки.

На Windows / реальном Ryzen / Pyannote / длинном аудио NOT_RUN.
Fast CI не доказывает работу GPU или браузерной интеграции.
